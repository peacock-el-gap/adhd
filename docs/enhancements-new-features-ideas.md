# Enhancements, new features, ideas

* **Log ADHD artifacts** - now we can see how ADHD artifacts changed over time if they are commited in git. But it will be easier if they are coppied along with logs. With timestamp in file name.
* **Package logs (and ADHD  artifacts) in directories** - When ADHD starts, it should create timestamped (sessiom start timestamp) directory in .adhd/logs/. Then all artifacts and logs should be located in such subdirectory. Each file should be timestamped (in file name) to reflect chronology and named to make it easy to identify which one is which one.
* **Incremental conversation log writes** - The conversation logger in `shared/conversation-logger.ts` accumulates events in memory and writes the markdown file only at the end, inside `finalize()`. Change it to write the header on creation and append each entry as it arrives (or batch-flush every few seconds). Lets the user follow a long agent turn with `tail -f` instead of waiting for the file to appear when the agent finishes.
* **`adhd status` command** - A read-only command that reports the current state of an in-flight run. It should read `progress.json`, locate the running harness process and its SDK subprocess, sample I/O counters on the SDK's network socket, and print: current phase, sprint and attempt, model in use, time elapsed in the current LLM call, last tool call observed, and inbound bytes per second. Answers "is anything happening right now?" in one command.
* **Stream-liveness watchdog** - A background loop in the harness that polls /proc/PID/io counters (rchar, wchar, syscr, syscw) every 30 seconds for the SDK subprocess and every descendant in its process tree. These counters aggregate all I/O — network reads, file reads, pipe traffic from child processes, output writes — in one set of numbers. After 5 minutes of stalled counters across the whole tree, log a warning. After 15 minutes, kill the entire descendant tree (SIGTERM, then SIGKILL after a short escalation) and surface the kill as a transient retryable error so the stage retries while preserving conversation state. Covers two failure modes in one mechanism: a slow or hung LLM response (no inbound bytes on the SDK's API socket) and a hung tool subprocess such as a test runner or shell command that keeps the SDK's stdout open after the LLM has already returned end_turn. Converts "is it stuck?" from an unbounded wait into a bounded, self-correcting condition.
* **Surface model thinking activity** - The Agent SDK emits events for thinking blocks (used by extended-thinking models), but the harness does not currently display them. Show a rate-limited terminal line every 30 seconds, for example: "GENERATOR thinking — 4 minutes elapsed, approximately 11 000 thinking tokens". Distinguishes "model is reasoning" from "process is stuck".
* **Structured reviewer output envelope** - Today the contract reviewer outputs either the literal string `APPROVED` or a full replacement JSON contract, with no record of what changed or why. Change the schema to a JSON envelope: `{ verdict: "approved" | "revised", changes: [short descriptions of what was changed and why], contract: <revised contract, only when revised> }`. Makes silent rewrites visible without changing the single-pass architecture.
* **`contract-diff` command** - When a sprint is re-contracted across multiple runs, separate negotiation logs are written but there is no easy way to compare them. A command like `adhd contract-diff <sprint-number>` should show the structural differences between successive contract versions for that sprint: criteria added, removed, renamed, or rephrased. Useful when debugging why the same sprint keeps being re-contracted.
* **Per-sprint token budget with soft limit** - A run with several sprints, retries, and an expensive evaluator model can consume substantial tokens. Allow the user to set a per-sprint token budget at run start. Warn at 80 percent of budget. At 100 percent, pause and ask the user whether to extend the budget or abort the run.
* **Feed evaluator failure feedback into the next generator attempt** - On a retry, the evaluator's specific reason for each failed criterion should be passed verbatim into the next generator's prompt as context. First audit whether this is already happening; if not, implement it. Reusing concrete failure details should improve retry success rates compared to a blind retry.
